# 지원 버전 정책

이 문서는 파이프라인의 버전 번호를 어떻게 매기는지, 파이프라인이 의존하는 Upstream 구성 요소(PyTorch, torch-mlir, NPU 개발 도구)의 버전을 어떻게 고정하고 추적하며 갱신하는지를 정합니다.

<br>

## 1. 파이프라인 버전 번호

버전은 `0.MINOR.PATCH` 형식이며, 1.0 이전은 기능과 명세가 계속 다듬어지는 단계입니다.

| 구분 | 올리는 경우 | 예 |
|:--|:--|:--|
| PATCH | 오류 수정, 문서 수정. 지원하는 Upstream 버전은 그대로 | 0.1.1 → 0.1.2 |
| MINOR | 기능 추가, 지원하는 Upstream 버전 변경, [NPU 특화 IR 명세](IR_SPEC.md)의 호환되지 않는 변경 | 0.1.x → 0.2.0 |

체험 이미지는 세 가지 태그로 배포합니다. `0.2.0`처럼 버전을 모두 적은 태그는 그 버전에 고정되고, `0.2`처럼 MINOR까지 적은 태그는 같은 MINOR 안의 최신 PATCH를, `latest`는 가장 최근 릴리즈를 가리킵니다. 사용 안내는 현재 MINOR 태그(지금은 `0.2`)를 기준으로 하며, MINOR 버전이 바뀌면 안내도 함께 바꿉니다. 버전별 변경 사항은 [변경 이력](../CHANGELOG.md)과 Release 페이지에 기록합니다.

<br>

## 2. 현재 지원 버전

| 구성 요소 | 지원 버전 | 비고 |
|:--|:--|:--|
| Python | 3.11 | |
| PyTorch | 2.3.0.dev20240122 (CPU) | 재구성 wheel |
| torch-mlir | 20240127.1096 | 재구성 wheel |
| NPU 시뮬레이터 | furiosa-opt 0.6.0 | Rust nightly-2026-05-01 |

### 하나의 버전으로 고정한 이유

- **변환 결과가 버전에 따라 달라집니다.** torch-mlir와 PyTorch는 버전마다 생성하는 표준 IR의 모양(연산 분해 방식, 행렬 곱 표현)이 다릅니다. 변환 규칙과 검증 기준값은 특정 IR 모양을 전제로 하므로, 검증한 버전에서만 결과를 보장할 수 있습니다.
- **변환 API가 바뀌었습니다.** 파이프라인이 쓰는 `torch_mlir.compile` API는 이후 torch-mlir에서 FX importer 방식으로 대체되었습니다. 최신 버전을 지원하려면 버전만 올리는 것이 아니라 변환 경로를 옮겨야 합니다.
- **원래 배포처에서 받을 수 없게 되었습니다.** 검증에 사용한 두 버전은 원래 배포처에서 더 이상 제공되지 않습니다. 재현성을 지키기 위해 검증 환경에서 wheel을 재구성하고, 재구성한 환경이 원래 환경과 바이트 단위로 같은 IR을 만드는 것을 확인한 뒤 [build-deps-1 릴리즈](https://github.com/soadri/ai-model-ir-pipeline/releases/tag/build-deps-1)로 제공합니다(SHA-256 고정).

<br>

## 3. 목표 정책과 단계

목표는 **PyTorch(이후 Triton 포함)의 최신 안정 버전과 그 직전 버전을 동시에 지원**하여, 사용자가 버전을 옮길 때 여유를 두는 것입니다. 현재 구조에서 바로 적용할 수 없으므로 다음 단계를 거칩니다.

| 단계 | 지원 범위 | 검증 방식 |
|:--|:--|:--|
| 현재 (0.2.x) | 검증한 단일 버전으로 고정 | 고정 버전으로 CI·Release 검증, Upstream은 매주 추적만 |
| 전환 | FX importer 경로로 변환을 옮기고, 최신 안정 버전 지원을 추가 | 고정 버전과 최신 버전의 변환 결과·검증 결과를 함께 비교 |
| 목표 | 최신 안정 버전과 직전 버전을 동시 지원 | 두 버전을 CI에서 함께 검증 |

전환 시기는 Upstream 변경 규모와 과제 일정에 따라 조정될 수 있으며, 조정한 내용은 이 문서와 변경 이력에 기록합니다.

<br>

## 4. Upstream 변화 대응 절차

Upstream 변화는 다음 네 단계로 대응합니다. 현재 자동으로 수행하는 부분과 관리자가 판단하는 부분을 함께 적었습니다.

| 단계 | 하는 일 | 주기 | 현재 수행 방식 |
|:--|:--|:--|:--|
| ① 모니터링 | 고정 의존성을 지금도 받을 수 있는지(체크섬, 철회 여부)와 Upstream 최신 버전을 확인하고, 변화가 있으면 알림 | 매주 월요일 | 자동: Upstream 변화 추적 워크플로가 Issue를 만들거나 갱신하고, 소개 페이지에 현황을 게시 |
| ② 영향도 분석 | 새 안정 버전에서 API, 연산 분해 방식, Dialect 정의가 바뀌었는지 분류 | 안정 버전이 나올 때 | 관리자가 Issue에서 검토 |
| ③ 대응 분류 | 작은 변경(패치, 문서)은 환경 파일에 반영하고 빌드를 확인. 큰 변경(API 구조 변경 등)은 영향 범위를 정하고 대응 계획을 세움 | 변경 규모에 따라 | 관리자가 판단, 계획은 Issue에 기록 |
| ④ 회귀 검증과 배포 | 핵심 연산(Attention 등)의 회귀 검증(Level 1-2, Level 3, 데이터 배치 연산 점검) 후, 정합성 결과를 Release 노트로 공개 | 버전을 갱신할 때 | 자동: Release 워크플로가 검증을 모두 통과한 경우에만 배포 |

<br>

## 5. 지원 종료

Upstream이 지원 종료(EoL)를 선언한 버전은 다음 MINOR 버전부터 지원을 종료하며, 해당 릴리즈의 Release 노트와 이 문서에 미리 알립니다. 재현성을 위해 이미 배포한 이미지와 고정 wheel은 지원 종료 후에도 내려받을 수 있게 유지합니다.
